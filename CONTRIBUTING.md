# Contributing to Runover Labs

Thanks for taking an interest. Contributions are welcome, though this is a
mostly single-developer organisation, so reviews happen when time allows.

## Before you start

- **Small fixes** (typos, obvious bugs, docs): just open a pull request.
- **Larger changes** (new features, refactors, behaviour changes): open an issue
  first so we can agree on the approach before you spend time on it.
- **Security issues**: don't file them publicly. See [SECURITY.md](SECURITY.md).

## Reporting bugs and requesting features

Search existing issues first. For bugs, include what you did, what you expected,
what happened, and your environment and version. For features, describe the
problem you're trying to solve, not only the solution.

## Pull requests

- Fork, branch from the default branch, and keep each PR focused on one change.
- Match the style and conventions of the surrounding code.
- Add or update tests and documentation where relevant.
- Make sure the project's tests and linters pass before submitting.
- Write clear commit messages that explain *why*, not only *what*.
- Link the issue your PR addresses.

## AI-assisted contributions

AI tools are fine to use, and no disclosure is required. Whatever you submit is
your responsibility: you should understand it, have tested it, and be able to
discuss it in review.

## Licensing

Unless a repository says otherwise, Runover Labs projects use the **MIT
License**. By contributing, you agree that your contribution is licensed under
the same terms as the project.

Guidance for new repositories:

- Default to MIT, and include a `LICENSE` file at the repository root.
- Where an upstream project's licence constrains derivatives (for example a
  plugin for a copyleft project), follow the upstream licence and note it in
  the README.
- Only depend on code whose licence is compatible with the project's.
